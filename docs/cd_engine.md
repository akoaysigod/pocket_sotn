# CD controller engine (design note, branch cd-engine)

`rtl/cd_top.vhd`'s command processor and drive state machine (about 2,000 ALUTs and 1,000 registers of
`cd_top`'s 2,700 / 1,480, measured by stubbing them out, see `docs/NIGHT_LOG.md`) are replaced by a small
microcoded engine. The CPU interface, the sector datapath, the FIFOs, the CD volume mix, the track table and its
search stay in hardware, unchanged.

## Timing model

The original processes compute, at every clock edge, the next value of their registers from the current state.
In the new design:

- **Fast path (hardware):** the per-clock rules that need no decision: counters (`cmd_delay`, `workDelay`,
  `driveDelay`) with their exact count / hold conditions, one-cycle pulses cleared again, `internalStatus_1`,
  `ackPendingIRQNext`, `newCD_1`, `Xa_playing`, `sectorBufferFilled`, `readSectorPointer` steps.
- **Events:** an edge at which the original would do more than that. Hardware detects them from the state before
  the edge (event vector), applies the fast path at the edge, latches the event vector and the state before the
  edge, and starts the engine.
- **Engine:** runs the original's actions for that edge (a translation of the process bodies) and writes the
  results straight into the engine-owned registers. While it runs, the engine-owned registers hold (no fast path):
  the engine's part of the controller is paused, so it behaves exactly as in the original, only later.
- **Simulation:** `sim/cd_equiv` holds the clock of everything else (CPU model, sector supplier, reference
  `cd_top`, the kept logic) while the engine runs, so engine time is invisible and the comparison with the
  reference is cycle exact.
- **Hardware:** the rest of the core keeps running; the engine's part lags by its run time (a few µs per event,
  far below drive timing jitter). Pulses from the kept logic that arrive meanwhile are latched (sticky).
  The command delays (`cmd_delay`, `workDelay`) pause too: they have decisions at exact values, and their lag does
  not add up. Exceptions (drive countdown, interrupts): see "Hardware-only behaviour" below.
- **Inputs the engine reads:** the event vector, this block's registers, the command and parameter bytes and
  the delay counters are latched at the edge (snapshots). The sector datapath's outputs (`lastReadSector`,
  `header`, `subheader`, `nextSubdata`), the track info and the volumes are read live: they change only while the
  datapath works or with the CPU's own commands, and the firmware reads each once per run where they may change.

## Engine (`rtl/cd_engine.vhd`)

- clk1x, accumulator machine, one instruction per clock, taken branches included (the next address is computed
  in the same clock and the program ROM is read with it).
- `A`: 32-bit accumulator. Flags: Z from every result written to `A` and from compares; C (carry, or borrow for
  SUB / CMP) from ADD, SUB, CMP.
- Operand `r` (7 bits): 0-63 register file (64 x 32 bit, MLAB, asynchronous read), 64-95 I/O port `r - 64`
  (reads: `cd_ctrl`'s read mux; stores: `cd_ctrl`'s write ports, one clock strobe).
- Program ROM: 40-bit words in M10K, depth a power of two (2,048 words: 8 M10K), generated by `tools/cdasm.py`
  from `rtl/cd_fw/cd_fw.py` (the firmware, written in Python) into the VHDL package `rtl/cd_fw_pkg.vhd`.
- Instruction word: `op[39:34] r[33:27] imm[26:0]` (immediates zero extended); jumps: target in the low address
  bits plus `bit[16:12]` (JBS / JBC) or `value[19:12]` (JEQ / JNE); LDB / MOVB: byte number in `imm[1:0]`;
  MOV / MOVB: destination in `imm[26:20]` (the operand `r` is the source).
- Operations (op codes in the header of `rtl/cd_engine.vhd`):
  - ALU, register or immediate source: LD, AND, OR, XOR, ADD, SUB, CMP, MUL (`A[26:0] * source[26:0]`, one DSP
    block; the assembler makes the left shifts with it)
  - SHR1, SHR8, LDB (a byte of the operand into A)
  - stores, which leave A and the flags alone: ST (A), STI (immediate), MOV / MOVB (another operand, or one of its
    bytes), SETB / CLRB (OR / AND of a register with the immediate), ORS (register OR A)
  - jumps: always, on Z, on C, on a bit of the operand, on operand = 8-bit value, each also inverted; WAIT ends
    the run
- Datapath: one source mux (operand / immediate / byte), one logic unit (also the stores, so the register file
  and the I/O ports are written from the result), one adder, the multiplier, the right shifter, a 4-way result
  mux. No call stack (the firmware has no subroutines).
- Assembler optimization (`Asm.optimize`): with a data-flow analysis of A, Z and C over all paths it turns
  `ldi; st` into STI, `ld; st` / `ldb; st` into MOV / MOVB, `ld r; ori / andi m; st r` into SETB / CLRB and
  `ld r; cmpi v; jnz / jz` into JNE / JEQ wherever the sequence's A and flags are not read afterwards and nothing
  jumps into it: 2,614 words become 1,894 (the ROM is 2,048 deep).

## Hardware-only behaviour (cd_ctrl / cd_top with SIM_FREEZE = false)

In hardware the rest of the core keeps running while the engine works, so the engine's part of the controller
lags real time by its run times. Where that would change what software sees, the hardware compensates:

- Drive countdown (`driveDelay`): keeps counting during runs; an engine write to it is reduced by the ce clocks
  the engine ran since its runs began back to back (a sector's countdown is loaded in the run after the
  drive-done run, one edge later in the original). Otherwise every sector would be a little late, and XA and CD-DA
  sectors come exactly as fast as they play: their buffers would run dry over minutes. The countdown only runs
  while `driveBusy` is set, so the firmware sets that flag before it writes the delay (the other order lost the
  clock between the two writes: one clock per sector, found with the SotN music script's XA monitor:
  225,793 instead of 225,792 clocks per sector).
- `ackPendingIRQ` -> `ackPendingIRQNext`: a one-clock pipeline with cd_top's interrupt logic (which would raise
  the delayed INT1 / INT2 again and again, and clear it, if the second half waited for the engine). It runs in
  real time; the engine gets the event at its next edge (kept while it runs).
- Interrupts: the original pushes an interrupt's response byte one clock after the pulse that raises it (or in
  the same clock); here that is the next engine run. From such a pulse to the end of the run after it,
  `cd_ctrl.quiet` is low: `cd_top` holds the pulse to the interrupt controller and the CPU reads the interrupt
  flags of the last quiet clock, so no interrupt is seen before its bytes. Only that one run: the engine can run
  every clock for a while (the drive waiting for an INT1 to be acknowledged), and a longer hold deadlocks. The
  exceptions: a CD-DA report, whose 8 bytes follow its INT1 on 8 edges, and Setloc / Setfilter, which read their
  parameters on the edges after their INT3 and reset the parameter FIFO at the last one. The firmware sets the
  `report` flag (`cdda_rep`) while report bytes are owed or parameter steps are left, and quiet stays low until
  then. Otherwise the CPU reads part of a report (the rest stays in the FIFO and the next reports are skipped), or
  writes the next command's parameters before that FIFO reset, which wipes them: SotN's Setfilter -> SetMode 0xC8
  then failed with INT5 03 20 (wrong number of parameters) and XA stayed off (found in hardware mode with the
  SotN music script, 2026-10-16).
- Pulses from the kept logic that come while the engine runs are kept until its next edge with ce.
- `sim/cd_equiv` with `CPUSRC=1` and without `FREEZE` runs this mode: the CPU model uses the engine instance; the
  summary (interrupts, answers, sectors, data and audio checksums, sector request count and timing) is compared
  with the same script's reference run. (The reference instance runs too, but its writes come at the engine's
  pace, so it may go astray; its outputs are ignored.)

## Status (2026-10-16)

- First hardware test (cdeC seed 1): boots and plays; music clicks, also on 0.1.4 (not the engine: slow SD reads and
  SPU timing, see docs/NIGHT_LOG.md 2026-10-16). Two hardware-only engine bugs found since with sim/cd_equiv's
  SotN music script and fixed (parameter steps hold interrupts; busy before the drive delay). Later builds:
  cdeE, cdeF, cdeG.
- Size: 17,518 ALMs in the fit (main's cc seed 1: 18,215), 262 M10K (+8: the program ROM), 54 DSP (-1); timing met
  at all corners (worst +0.028 ns, not in the CD logic). Quartus map, whole core: 26,813 ALUTs (-986),
  21,366 registers (-99); cd_top 2,473 ALUTs (was 3,458), of which engine 414, cd_ctrl's own ~400.
- `sim/cd_equiv` FREEZE (every output, every clock, against `ref/pocket/rtl/cd_top.vhd`): boot, SotN-like +
  XA, CD audio: 0 mismatches with the final RTL; random commands (seeds 1, 2, 3, 5, 6, 7 on the engine's
  development versions, with ce bursts, one without a disc; seed 4 on the final RTL): 0 mismatches. Two
  deliberate firmware bugs (an interrupt one clock late, a read LBA + 1) are caught.
- `sim/cd_equiv` CPUSRC=1 (hardware mode) against the reference's summary: boot identical (44 interrupts, 16
  sectors, same data checksum); CD audio identical (30 interrupts incl. 14 reports, 91 sector requests,
  50,769 / 50,755 samples); SotN-like the same but one more INT1 before a timed Pause.
- `pocket/sim/boot` (whole core, BIOS, no disc): the same progress at every report to 400 ms as with the old
  controller.
- The old controller is one file swap away: `ref/pocket/rtl/cd_top.vhd` (and drop cd_fw_pkg, cd_engine, cd_ctrl
  from `pocket/src/fpga/psx_pocket.qip`).
